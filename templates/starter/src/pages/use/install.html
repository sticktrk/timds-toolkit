Paste one address

For a one-off, hand any AI tool that can read a URL the system's llms.txt. The file opens with how to use itself, then the brand essentials: every role color, every font and where it comes from, every logo, every asset format, and the directory of these pages. Paste the line below into the chat and finish it with the work you want.

Read https://THIS-SYSTEM/llms.txt and follow it. Then: …
AddressHoldsUse it when
llms.txtHow to use the file, the brand essentials, and the page directory with a link to each page's Markdown.Most one-off work. The tool follows a link only for the detail it needs.
llms-full.txtEvery page's Markdown in one file.A tool that reads a single URL and cannot follow links, or work that touches the whole system.

Both files are regenerated on every release and carry absolute addresses, so either one can be handed around on its own. Nothing is installed and nothing is pinned: the next paste reads the next release. Ask the tool to name the version it read; it is on the file's first lines.

Connect your agent over MCP

For ongoing work in a repository, add the system's read server to the agent once. The entry runs the TimDS CLI at @latest against the published copy, so there is no version to maintain, no sign-in, and no token: the server is read-only and never sees authored source. It is named timds-design-system-read; its first calls are get_consumer_guide, then describe_system, and every result names the release it read. Pick the tool, copy the snippet, and start a new conversation in the repository.

Snippets 1 to 6 give the agent the whole consumer tool set: brand roles, tokens, guidance search, pages, formats, designs, and media; Using the system lists every tool. Snippet 7 needs nothing on the machine and carries the host's published read tools, describe_system, get_tokens, read_page and read_derived_layer, each taking this system's id, SYSTEM-ID, as systemId and an optional version.

First reads, in order: get_consumer_guide once per conversation, then describe_system and note the version. For a color or a font ask resolve_role, not a token name; for marks and imagery get_brand and list_media; for copy search_guidance; for a size list_formats. Report what was used, and name anything the system could not answer rather than guessing it.

When the release is an offshoot, describe_system and the derived layer's provenance carry lineage: its parent system, source, release, commit, and creation mode. A null lineage is supported for ordinary systems and older releases. Ancestry describes where the system began; use the served system's guidance and assets.

Pin a release in a website or app

A product never copies the system. One command at the product's root pins the current release in timds.consumer.json, wires a digest-verified fetch of the consumer bundle into npm install, installs the timds-consume-design-system skill that tells an agent how to make a design change in the product, and writes the MCP entry from step 2. A clone and an install is then all a developer, or an agent working in the product, needs.

npx --yes @dtconcepts/timds@latest consumer init --system SYSTEM-ID --url https://THIS-SYSTEM
npm ci
ThenCommandDoes
Move the pinnpm run timds -- consumer updateMoves to the current release, or to the version named after it. A pin of current follows every release at the next install.
Checknpm run timds -- consumer checkValidates the manifest and the pin, and that a branch stays inside the product's declared design surface.
Reviewnpm run timds -- consumer preview --app NAMECaptures each route at desktop and phone widths beside its paired design.

In product CSS use a token by name, never by its literal value, so the product follows the pin. SYSTEM-ID is this system's id, the one .timds-artifact.json beside this page names; a browser fills it in above. Using the system has the full product workflow.

Give your agent the designer skills

Changing the system is a different job from using it: it happens in the system's repository, through a session the host reviews, and this published copy is read-only. Install the designer skills once in the folder the agent works from, with the authenticated host your operator gives you. The skill has the agent sign in as you, start a session, bring up the local preview, and submit for review when you say so.

npx --yes @dtconcepts/timds@latest skills install --portal-url https://YOUR-HOST --system-id SYSTEM-ID

The skills land in .agents/skills/, .claude/skills/ and .cursor/skills/; --global puts them under the home folder instead. YOUR-HOST is the host's authenticated origin, not this public address: Studio's Send your agent… button produces a brief with it filled in. Using the system covers the other ways the system changes.

Stay current

Every way in reads the current release by default, and nothing above pins the toolkit. Each merged change becomes a new release that the next read picks up.

Way inOn a new release
One addressNothing to do. The files are regenerated with each release.
An agent over MCPNothing to do. The server runs at @latest and serves the current release; pass version to read an earlier one.
A pinned productMove the pin with consumer update when the developers are ready; the changelog lists what changed in between.
Designer skillsRerun skills install; it refreshes unmodified files and keeps edits.
